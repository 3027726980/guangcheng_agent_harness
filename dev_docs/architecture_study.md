# 十道架构题具体回答

作者：LHF。更新日期：2026-10-23。

本文给出五个模块、十道题的完整回答，供逐题理解后选择使用。回答中的“我会”表示设计选择，“项目已实现”表示当前工作区已有代码；方案参数是初始配置，不是实测最优值。项目现阶段是单进程、自写 Runtime、SQLite 存储，没有跨会话长期记忆、独立 Goal、后台 Job 和定时调度器。本文仅修改文档，没有启动服务或执行真实模型与性能测试。

## 模块一：Context / Performance

### 1. 第一轮长窗口／多模态输入，如何把首字延迟从 5–10 秒降到约 2 秒？

我的方案是减少首次推理实际处理的输入，复用稳定前缀，并直接流式展示正文。首先把指标定义为“用户点击发送，到第一段有效正文开始展示”，同时单独记录请求确认和首个思考输出；加载动画和“正在分析”不算有效首字。

具体执行过程如下：

1. 用户选择附件后就开始上传和可复用的文本提取，保存文件内容哈希及处理结果；发送问题时复用已经完成的处理。用户直接粘贴的长文本仍需在发送后处理，不能假设已提前准备。
2. 对资料定位型问题，先用本地索引或关键词筛选相关段落，按问题、必要约束、相关片段和来源组成输入。例如用户问五十页合同中的退款条件，默认只发送相关条款及解释它所需的上下文，并提供读取其他段落的入口。
3. 对全文比较和完整审阅问题，保留必需范围，不能为了速度只检索几个片段后声称已经读完全文。图片任务按问题裁切区域、控制分辨率，并缓存 OCR／抽取结果；需要比较的关键区域全部保留。
4. 系统提示与工具定义保持稳定顺序，动态问题和检索资料放在后面，增加重复前缀被供应商缓存复用的机会。第一轮独有的长文本按未命中缓存计算，不把重复测试的热请求当成首次请求。
5. 默认使用质量足够的较快模型；简单提取任务关闭不必要的推理。不给模型额外增加“先规划一次、再正式回答一次”的串行调用，也不要求精确字数等会诱发反复计数的无关约束。正文到达后直接向前端流式转发。

两秒目标必须带适用条件。我会先规定模型、输入上限、网络和并发，再把应用传输与展示、资料准备、上游首段正文分别设为约 0.2 秒、0.3 秒、1.5 秒的设计预算，采集各段实际耗时并验收总体 P95。这些数字是验收预算，不是已实现结果；首次 OCR、冷索引构建或完整长文审阅超过预算时，应明确展示处理阶段，不能承诺任意输入都稳定两秒。

项目已有流式输出、模型请求快照和上下文估算，可以从这些入口补分段时间；多模态和上述附件预处理尚未实现。DeepSeek 的供应商缓存用于减少重复前缀计算，Harness 的 Context／spill 用于控制输入内容，这两层可以配合，但不能把缓存当作冷请求的保证。

参考：[DeepSeek 缓存机制](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)、[Harness 全文外置](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/spill/README.md)。代码：[请求快照](../backend/app/request_capture.py)、[模型流式适配](../backend/app/llm.py)。

### 2. 一个 Session 连续聊了 200 轮，Context 快满了，如何压缩并保证追问流畅？

我会采用“完整历史持久化＋增量摘要＋近期完整交互”的方案，按 token 压力触发，不按固定轮数删消息。数据库保留原始消息和工具结果，模型只看到当前可见的摘要及消息后缀。

以容量 32,000 tokens 为例，本地预留 3,200 输出空间和 1,600 安全余量，得到 27,200 的输入预算。在包含系统提示、工具定义和历史的输入估算达到 21,760，即可用输入预算的 80% 时触发压缩，按 13,600，即 50% 目标选择保留范围。这对应项目默认比例；目标并非保证，必要内容较多时允许高于目标，但不能超过输入预算。当前不向供应商发送固定输出上限，因此本地预留也不能证明生成过程一定不会超限。

执行时，我会先处理过大的工具正文：全文保存，模型保留关键字段、预览和读取位置，然后重新计算容量；仍超阈值才摘要较早历史。摘要固定保留用户目标、约束、明确修正、关键事实、来源、业务 ID、确认操作、失败／取消和未完成事项。当前请求、有效引导和近期交互优先保留；assistant 工具调用与对应全部 tool 结果作为完整块处理。

摘要成功后检查四件事：结束原因正常、内容非空、重组输入可放入、被压缩范围没有被并发修改。全部成立才在事务中更新摘要和可见清单；否则保留原历史。摘要失败时，原输入还能容纳就继续，不能容纳就停止并说明原因。对于单个超过摘要模型容量的不可拆交互，不强行截断成非法工具消息。

例如前文已经创建待办 T17，用户追问“把它改成周五”，摘要至少保留 T17 的标识、归属和之前确认的操作；真正修改前仍查询最新版本，不能直接使用摘要里的旧状态。检验压缩质量时，我会专门检查这种指代、数字、用户改口和已取消操作能否正确延续。

项目已实现预算触发、完整工具分组、独立摘要模型、分批归纳和 Context 版本校验；工具结果通用外置仍是扩展项。我借鉴 DeepSeek Harness 将工具结果裁剪与模型摘要分开的方式，优先减少不必要输入，再支付摘要模型成本。

参考：[基础压缩](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/compaction-basic/README.md)、[工具结果裁剪](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/compaction-tool-result-pruner/README.md)。代码：[ContextManager](../backend/app/context.py)、[可见清单与事务](../backend/app/session_context.py)、[摘要提示词](../backend/app/prompt/summary.py)。

## 模块二：Memory

### 1. 和 Agent 熟悉半个月后，用户再次提出以前的问题，如何召回？

我会采用“少量稳定偏好预取＋按需检索历史原文”的混合方案。重复提问时先判断用户是在沿用旧决策、查找过去记录，还是询问当前事实；不因为问题相似就直接复制旧答案。

写入时保存经过确认的偏好、事实和决策，每条包含 user_id、内容、类型、来源消息、确认时间、有效范围、有效期及被哪条新记录替代。初版在一轮交互结束后批量提取，减少每条消息单独评分的成本。用户明确更正时立即使旧条目失效并更新索引；原始聊天是否保留按历史保存规则另行处理。

召回时先按用户和授权范围过滤。与当前任务有关的固定偏好少量预取；问题出现“上次、之前、那份方案”等历史指向，或模型需要核对旧决策时，再通过历史搜索工具查关键词、实体和语义候选。初始配置取前 20 个候选，经去重、相关性、有效期和用户修正筛选后，最多注入 5 条，总预算约 1,500 tokens；这些值后续按评估调整，不把相似度阈值当成事实可信度。

注入内容使用明确标识的历史资料，附来源和时间，放在系统提示之后、当前问题之前。信息冲突时优先采用范围匹配的较新明确修正；无法判断则读取原文或询问用户。价格、库存、待办状态等动态信息直接查最新业务来源，旧记忆只帮助定位。

例如用户半个月前问“方案用 SQLite 还是 PostgreSQL”，当时选择 SQLite 的条件是单进程、本地演示。今天再问时，如果条件未变就沿用原决策并解释依据；如果今天要求多实例部署，就重新评估，不能让旧答案压过新需求。

项目当前只恢复本 Session 的消息和摘要，没有这套跨会话记忆。我会先增加用户隔离的历史检索与原文读取，再建设事实提取和偏好存储。DeepSeek Harness 的可选历史查询工具提供了按需找旧会话证据的参考，但其工作区访问规则不能直接替代本项目的用户权限规则。

参考：[Harness 历史查询](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/experimental/tool-session-query/README.md)。代码：[当前 Session 记忆恢复](../backend/app/session_context.py)。

### 2. 你理解的 Agent Memory 经典框架、发展方向和代表实现是什么？

我把 Agent Memory 理解为“工作上下文＋外部持久记忆＋读写管理策略”。工作上下文保存当前任务需要的内容；外部记忆保存可跨任务复用的信息；策略决定什么时候保存、更新、召回和删除。向量数据库只是其中一种检索组件。

经典分类可以对应到具体数据：工作记忆保存当前请求和近期工具交互；语义记忆保存用户偏好与事实；情景记忆保存某次任务的条件、操作和结果；程序性记忆保存可复用规则与技能。落地时我不会为每类都建立独立数据库，而是在统一记录中增加类型、范围、来源和版本，并让最新业务状态继续由业务数据库负责。

整个闭环是：交互产生证据，筛选值得保存的信息，写入或更正记忆；新任务到来时检索、核验时效与权限，再把必要部分放入 Context；任务结果继续反馈到记忆。模型猜测、计划和成功工具结果要分开记录，避免把“准备做”长期保存成“已经做”。

我会比较这些有代表性的实现路径，而不宣称谁在市场排名第一：

| 实现 | 公开设计中的重点 | 对本项目的借鉴 |
| --- | --- | --- |
| LangGraph | 线程内状态与跨线程长期记忆分开 | Session 状态与跨会话知识分别管理 |
| Letta | Agent 的持久可编辑记忆，常驻内容与按需读取内容区分 | 固定偏好少量常驻，大量细节外置 |
| Mem0 | 从交互提取信息并提供独立记忆存取能力 | 将记忆提取和检索从 Agent Loop 中分离 |
| DeepSeek Harness | Session 历史、压缩、历史查询和 Goal 各自管理 | 不用一份摘要承载所有执行和记忆状态 |

从这些设计可以归纳的方向，是从“尽量记住全部历史”转为“选择性写入、按需读取、可更新和有来源”，并把巩固整理放到合适的后台阶段。其收益需要用召回准确性、过期事实干扰、更正与删除生效、延迟和成本衡量，不能只统计记忆条数。

对当前项目，我选择先维持已有 Session 摘要，再加入历史搜索和少量用户偏好；长期目标单独记录为 Goal，待办仍从数据库查询。这样扩展记忆时不改变主循环的基本职责，也不为尚未出现的需求引入完整记忆平台。

参考：[LangChain Memory](https://docs.langchain.com/oss/python/concepts/memory)、[Letta Memory](https://docs.letta.com/agent-sdk/memory)、[Mem0 记忆写入](https://docs.mem0.ai/core-concepts/memory-operations/add)、[Harness Session](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md)。

## 模块三：Task

### 1. 长程任务执行一段时间后忘记目标，如何解决，有什么取舍？

我会增加独立的持久 Goal，并将长任务拆成带验收条件的阶段。Goal 保存要达成什么，Run 保存一次执行发生了什么；一个 Goal 可以关联多个 Run。不会把用户业务 todo 当作内部目标管理器。

Goal 至少保存目标、用户约束、完成标准、阶段列表、当前阶段、已有产物与证据、未完成事项、阻塞原因和状态。每次模型调用前把当前目标、约束、当前阶段及未完成项作为简短任务资料放入 Context，详细过程按需读取。内容由独立记录生成，不依赖旧聊天有没有被摘要保留。

例如任务是“整理客户问题、生成报告并验证文件”，我会分成读取资料、整理分类、生成产物、验证交付四个阶段。生成报告后保存文件引用，验证后保存实际检查结果；若文件生成成功但验证失败，前一阶段保持完成，当前阶段记录失败原因。恢复时核对产物和已提交操作，只补未完成部分。

每个阶段结束都检查目标和约束是否仍成立。计划调整记录原因；写入操作使用独立操作标识，恢复前查询是否已经提交，不直接重跑。只有所有必要产物和验收条件成立才将 Goal 设为完成；模型输出最终文本、Run 预算耗尽或进程退出，都不等于目标完成。

续跑由独立驱动器决定：有未完成步骤、没有暂停或阻塞、仍有累计预算时，创建下一次 Run；到达预算上限就停止自动继续并保留进度，需要用户补充的条件则进入阻塞状态。项目重启后默认恢复记录，待核对外部状态并明确恢复执行后再继续。

短检查清单成本最低，但容易假完成；阶段规划可以减少单次上下文，却增加交接和规划成本；持久检查点有利于恢复，但必须处理幂等。我会选择“持久目标＋短阶段清单＋阶段验证”，默认仍由一个 Agent 顺序执行，只有独立工作确有并行收益时才拆分。

项目已有 Run、预算和工具证据，但没有 Goal 和自动续跑。DeepSeek Harness 将 Goal 与 round driver 分开的方式适合借鉴：保存目标不意味着已经调度执行，完成当前轮次也不意味着长期目标完成。

参考：[Harness Goal](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/goal/README.md)。代码：[当前 Run 模型](../backend/app/run.py)、[主循环与预算](../backend/app/runtime.py)。

### 2. 每天早上 9 点根据昨天聊天做复盘，如何设计？

我会采用“持久调度记录＋到期任务领取＋现有 Runtime 总结＋结果和通知分别保存”的方案。初版直接用现有 SQLite 加一个调度扫描器，不先引入独立消息中间件。

创建调度时记录 user_id、目标 Session、时区、每天 09:00 的本地规则、next_run_at、读取范围、输出位置和启用状态。时区默认使用用户确认的 Asia/Shanghai；以后支持其他时区时按本地日历计算下一次触发，不能简单每天增加 24 小时。

扫描器例如每 30 秒检查到期记录，在事务中创建唯一执行键 schedule_id＋本地总结日期，并领取带过期时间的租约。同一个日期只能有一条执行记录；进程崩溃后由恢复逻辑核对结果和租约再决定是否重试。调度配置保存“每天九点”，与实际执行可能晚几十秒分开记录。

执行时读取该用户昨天 00:00 至今天 00:00 的有权访问聊天，转换成 UTC 查询，按 Session 和完整工具交互分批归纳，再汇总完成事项、决策、问题和后续行动，并保留来源消息。结果唯一关联本次执行键。没有聊天时记录空结果，不额外唤醒模型，也不发送无内容通知。

我为初版选定的补跑规则是：当天恢复后补跑今天漏掉的一次，不批量追补更早日期；例如九点离线、十一点恢复，会总结昨天一次。已经成功的结果不因重新扫描而重做；用户更正或删除来源后，需要时显式生成修订版本并重新核对访问权限，不能继续展示已无权访问的原文。

结果与待投递通知在同一事务中保存，通知发送失败只重试通知，不重新总结。初版只在应用内通知；邮件等外部渠道另行授权。通知携带唯一事件 ID，前端重连后可以去重并读取已保存结果。

DeepSeek Harness 的 Schedule 也是到期向原会话交付 follow-up，再由 Agent 执行后续工作。本项目当前没有调度，而且聊天 Run 依赖客户端连接，因此需新增后台执行归属与提交入口，复用主循环但不依赖浏览器在线。

参考：[Harness Schedule](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/schedule/README.md)。代码：[现有存储与事务](../backend/app/storage.py)、[Runtime](../backend/app/runtime.py)。

## 模块四：Tool / Session Runtime

### 1. 异步工具不能让用户一直等，如何执行和完成通知？

我会把真正长时间的工具设计成“提交后返回 Job ID”。普通短工具仍在当前轮次 await；需要几十秒到几分钟的导出、渲染或批处理，提交后由后台执行，当前对话先说明已接受任务及状态入口。异步函数语法本身不提供这套后台语义。

提交工具先保存 Job，字段包括 job_id、user_id、session_id、origin_run_id、输入引用、幂等键、状态、进度、超时和结果位置，再返回 job_id 与 queued 状态。该返回就是本次工具调用的合法 tool 结果，原调用至此完成；后台最终结果不冒充同一调用的第二条返回。

初版使用进程内 Worker 领取数据库里的 queued Job，原子地改成 running。提供查询和取消接口，执行过程通过 SSE 展示真实阶段及进度。完成时将终态、结果位置和待投递完成事件写入同一事务，投递器随后向所属 Session 发送事件；事件可以重复送达，消费按 job_id 和事件 ID 去重。

如果后续只需用户下载结果，界面直接展示结果通知，不调用模型；如果用户原始任务要求“导出后再总结”，完成事件通过 Session 串行入口创建一次关联 Job 的后续 Run，由 Agent 读取结果继续处理。需要继续处理的事实及其一次性领取状态持久保存，避免重复事件启动两次后续执行。

用户停止原 Run 时是否取消 Job，要由创建时的生命周期策略决定。初版普通导出允许在当前回复结束后继续，用户可单独取消；取消先记为 cancelling，确认执行停止后再记 cancelled。外部效果已经发生或结果无法确认时如实记录，不宣称已经撤销。

进程退出后不能让数据库里的 running 永久悬挂。初版将遗留执行标为 interrupted 或结果未知，读取已保存的产物和操作记录；确认可安全重试的任务才重新排队。非幂等写入需核对外部状态，不能自动重放。以后需要跨进程执行和资源恢复时，再接持久队列与独立 Worker。

DeepSeek Harness 的 Job 注册、归属和完成通知提供了参考，但其 jobs-local 是进程内实现，不能据此声称执行可跨重启恢复。本项目当前只并发同批独立只读工具并等待整批完成，尚未实现这里的后台 Job。子 Agent 只适用于确实需要独立推理的工作，普通批处理直接交给 Worker。

参考：[Harness Jobs](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/jobs/README.md)、[生命周期记录](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/jobs.md)。代码：[当前工具批次执行](../backend/app/runtime.py)。

### 2. Session 为 Busy 时，用户新消息和异步完成事件同时到达，Runtime 如何处理？

我的规则是“同一 Session 单入口串行推进，普通消息排队，引导在步骤边界生效，后台结果先保存再决定是否唤醒”。不同 Session 仍然并行。Busy 是执行情况的展示，不能代替输入归属和调度规则。

所有已接受输入记录 session_id、来源类型、关联 Run／Job、顺序号和去重标识。普通用户消息排成独立 Run，在当前执行及收尾结束后领取，执行前不提前放入模型 Context。用户明确将消息转为引导时，原子地从独立队列移除，绑定当前 Run，防止相同内容既作为引导又执行一次。

引导在当前模型请求或工具批次结束后的边界应用，然后重建 Context。后台完成事件先更新 Job 并记录可读取结果：只补充资料的事件等待下一次模型调用，不单独唤醒；需要继续用户任务的事件入队一个后续 Run；只需要交付文件的事件直接通知。不会把所有 Job 完成都无条件塞入正在处理的无关任务。

停止请求走独立控制通道，及时设置取消意图，但进入数据库事务提交等不可回滚边界时要等待结果明确。完成判定和引导接收共用短控制锁：若引导先被接受，当前 Run 必须继续处理；若 Run 先完成提交，新的引导转换被拒绝，原排队消息保持排队。这样最后一个 token 与新消息同时到达也有确定结果。

例如 Run A 正在执行时收到新任务 B，以及旧 Job J 的完成事件：B 排队；J 的结果先保存。J 若只需通知，就直接展示；若还要后续推理，则关联 J 创建任务 C，按入队顺序在 A 结束后处理。用户明确补充给 A 的限制作为引导在 A 下一步骤生效，不能被普通 B 混入。A 已取消时，J 晚到也不能恢复 A。

DeepSeek Harness 的 followup、steer 和 inject 分别表达后续任务、最近步骤引导和不主动唤醒的上下文资料。我会借鉴其语义，在本项目现有 lane、引导和控制锁上增加持久完成事件。模型网络等待不占用控制锁；写入共享 todo 仍使用业务事务、操作幂等和版本检查，不能仅靠 Session 串行保证跨窗口一致。

项目已实现普通排队、引导、取消及完成前检查，尚无 Job 完成事件通道。多实例扩展时还要将 Session 所有权和任务领取放入数据库或队列，进程内锁不能跨实例协调。

参考：[Harness 输入与唤醒契约](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md)。代码：[lane 与引导处理](../backend/app/runtime.py)、[todo 并发控制](../backend/app/tool/todo.py)。

## 模块五：Agent Runtime 架构对比

### 1. Claude Code 的工具输出方式与 GLM／豆包等兼容 Function Calling 有什么不同，各有什么优缺点？

我会先区分产品展示和模型协议。Claude Code 是带工具执行与终端界面的 Agent 产品，GLM／豆包是模型服务类别，终端显示工具文字或卡片并不能说明模型采用纯文本调用。能从公开资料准确比较的是 Anthropic 工具协议与兼容 Function Calling 协议，不能据此断言 Claude Code 所有私有内部实现。

两者都通过“工具定义→模型生成结构化调用→客户端执行→按调用 ID 回传结果→模型继续”工作，主要区别是消息组织方式：

| 项目 | Anthropic 内容块协议 | 常见兼容 Function Calling |
| --- | --- | --- |
| 工具声明 | 名称、描述与 input_schema | tools 中的 function 及 parameters |
| 模型请求工具 | assistant 内容中的 tool_use 块，带 id、name、input | assistant.tool_calls，带 id、函数名和 arguments |
| 参数形态 | 完整消息中 input 为结构化对象；流式仍需累积参数片段 | arguments 常为 JSON 字符串，流式累积完整后解析 |
| 结果回传 | user 消息中的 tool_result 块，通过 tool_use_id 关联 | role=tool，通过 tool_call_id 关联 |
| 工程优点 | 文本、图片及工具块可以统一组合 | SDK 与兼容服务接入成本较低 |
| 工程成本 | 需理解内容块、块类型及配对规则 | 兼容接口的扩展字段和行为仍需逐家核验 |

我的项目选择兼容接口，因为首版需要用较小适配成本接入模型。LLM 适配层把供应商响应转换为统一的 ModelReply，Runtime 只处理正文、调用、结束原因和用量。先累积完整调用，检查结束原因、参数、工具名称和重复 ID，再执行；前端工具卡片来自执行事件，不根据模型声称“已执行”生成成功状态。

已知供应商要求的原生 reasoning_content 单独保存并回放，展示文本另行处理；不把这种兼容规则推广成所有模型的共同要求。后续接入 Anthropic 时新增协议适配器与必要内部内容类型，复杂多模态信息不能强行压成一个 text 字段。

工具超时、权限、并发、取消和大结果外置都属于 Runtime 等执行层的职责。DeepSeek Harness 将模型服务、适配器、工具和循环分开，也说明协议不同不要求重复实现整套执行器。我的取舍是保留统一循环和工具契约，让供应商差异收敛在适配边界。

参考：[Anthropic Tool Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)、[GLM Function Calling](https://docs.bigmodel.cn/cn/guide/capabilities/function-calling)、[Harness 分层](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/README.md)。代码：[模型适配](../backend/app/llm.py)、[响应契约](../backend/app/schemas.py)、[工具注册表](../backend/app/tool/registry.py)。

### 2. OpenHands 状态机的优缺点是什么，更合适的实现方式是什么？

状态机是把允许的状态与转移条件显式写出。例如任务从 queued 进入 running，用户停止后进入 cancelling，确认收尾才进入 cancelled；不能仅因为收到停止请求就假设外部操作已终止。

本次参考的是 OpenHands 软件 Agent SDK 的 conversation/state.py，其中包含 IDLE、RUNNING、PAUSED、WAITING_FOR_CONFIRMATION、FINISHED、ERROR、STUCK、DELETING 等执行状态，并结合事件日志。它的优点是运行、暂停、等待确认和异常有共同语义，UI 与控制逻辑能按状态做确定处理，便于排障。代价是增加一种能力时需要维护更多转移规则，并在取消、确认和完成并发发生时保持一致。

我不会简单删掉状态机，而会把不同职责拆开：

| 对象 | 管理的状态 |
| --- | --- |
| Session 调度器 | 当前执行归属、输入队列、是否允许推进 |
| Run | queued／running／cancelling 及完成、取消、失败、受限、中断等终态 |
| Job | 排队、运行、停止中及独立执行终态 |
| Goal | active、paused、blocked、completed 等目标状态 |
| Connection | 连接在线与否，不直接代表任务完成 |

所有状态修改通过 Session 的串行入口和明确的转移函数执行，提交前检查当前状态和版本。事务先保存必要记录及待发事件，再发布通知；工具和模型等副作用执行完，以带 Run／Job 归属的结果返回。旧执行结果不能覆盖新任务，同一个终态事件重复到达也不能重复触发后续动作。

例如“报告正在后台导出，当前聊天已经结束，目标还需要验证文件”，应表示为 Run completed、Job running、Goal active。若都塞进 Session 的单一枚举，就需要不断增加“聊天已结束但后台运行且目标未完成”这类组合。按对象拆开后，各对象的转移规则更容易验证，也能在界面分别展示。

DeepSeek Harness 的 Agent 公共状态主要是 idle／running，具体过程由 turn、step、Job、Goal 和事件记录表达；它减少的是顶层状态负担，没有消除底层生命周期。例如 idle 下仍可能运行维护任务，因此能否启动其他操作仍需检查具体所有权和执行契约。

当前项目已使用类型化 Run、Session lane、短控制锁和 SQLite，尚无完整事件溯源。我会先集中并审查这些转移边界，补 Job 和 Goal 时继续独立建模；只有确有重放或多实例要求时才引入持久事件驱动和原子领取。完整事件溯源还需承担事件版本迁移、重放兼容和副作用幂等成本，不能仅为了状态名更少就迁移。
