# 十道架构题研讨材料

日期：2026-10-20。用途：逐题理解和讨论，最后每个模块由毛毛选择一道，共五道。这份材料不是代替个人判断的最终答卷；根目录 `架构设计回答.md` 暂不填写。

“本项目已实现”和“可扩展方案”分别标明。资料用于核对机制，不将某个项目的设计直接当成唯一答案，也不把推测写成实测结论。

## 模块一：Context / Performance

### 1. 第一轮长窗口／多模态输入，如何把首字延迟从 5–10 秒降到约 2 秒？

先定义指标：服务确认接收、展示处理进度、模型产生第一个有效回答，是三个不同时间点。先回一句“正在分析”可以降低等待的不确定感，但不能算模型首字变快。稳定 2 秒必须明确模型、输入规模、网络、并发和命中率，再测 P50/P95；不能只靠一个流式开关作保证。

分解耗时为客户端上传、排队、输入预处理、模型 prefill 和第一步解码。按实测瓶颈选择措施：

- 文本只装入当前问题需要的资料；大文件先检索定位段落，不把所有附件逐轮发送。误删约束会影响正确率，因此保留来源和再次读取入口。
- 固定系统提示和工具定义保持稳定前缀，利用供应商支持的缓存；首轮用户新上传内容通常不能假定已有缓存。缓存命中需观测，不能靠缩短展示文案来推断。
- 图片按任务选择分辨率、裁切、数量；OCR、索引或抽取可复用。第一次处理仍有成本，而且不能为了速度删除用户要比较的关键区域。
- 独立预处理可并行；轻量模型处理确实简单的任务，但需要质量回归和回退路径，不能为了快对同一问题先后调用两个大模型。
- 立即反馈接收状态和真实进度，在流式结果到来后持续显示。这改善体验，性能指标仍单独记录。

本项目：已有流式输出、Trace、上下文裁剪和预算；没有多模态、缓存效果评估或 2 秒服务承诺。下一步应先加耗时分段和固定输入集，再比较延迟／成本／质量。

讨论重点：题目说的“2 秒”究竟是有效首字还是界面响应？如果上游最低 prefill 就超过 2 秒，你会如何向产品解释边界？

参考：[OpenAI 延迟优化](https://developers.openai.com/api/docs/guides/latency-optimization)、[Anthropic Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

### 2. Session 连聊 200 轮如何压缩，如何保证追问流畅？

按实际 token 预算触发，比按“200 轮”更准确：一轮可能只有一句话，也可能带一整份工具结果。原始消息不可变地保存在数据库，模型窗口使用“历史摘要＋未覆盖的近期消息＋当前任务关键输入”。

摘要应保留目标、限制、确定事实、用户修正、实体与来源、已完成操作及证据、失败／取消、未完成项。工具调用和对应结果作为完整块处理，避免模型收到没有对应调用的 tool 消息。当前请求和引导受保护，当前任务较早的已完成步骤也可摘要。

每次模型调用前检查容量，预留输出及估算余量；超阈值后增量摘要并记录真实覆盖的消息 ID。只有完整成功、最终输入仍可放入时才提交新摘要。摘要失败且原输入还能放入则使用原输入，放不入则保留历史并明确停止；不能不断重试直到预算耗尽，也不能宣称压缩无损。

追问验收应覆盖代词指代、数字、用户改口、工具返回 ID、操作状态和被停止的任务。摘要中的“待办未完成”可能已经过期，下次操作先读真实待办，不把摘要当数据库。

本项目：上述基础机制已实现，包括独立摘要模型容量和分批摘要；80% 触发、50% 为目标，必要输入较多时不保证一定到 50%。没有长期事实库和语义召回。

讨论重点：哪些信息值得固定保留？如果单个不可拆工具块已经超过容量，应该截断、外置还是停止？首版选择停止，后续可将大结果外置并提供按需读取。

参考：[LangChain Summarization](https://docs.langchain.com/oss/python/langchain/middleware/built-in#summarization)、[Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

## 模块二：Memory

### 1. 半个月后重复提问，如何召回更合理？

先区分“相同文字”和“同一意图”。用户重复问价格，可能需要今天的新价格；用户再次问个人偏好，可能希望沿用已确认的选择。因此应同时判断事实时效和用户意图，不能命中旧问句就直接复制旧答案。

可扩展流程：对当前用户和权限范围构建检索查询，结合关键词、向量相似度、时间和实体找候选；按相关性、可信度、时效、用户明确修正重排；只把必要的少量记忆作为带来源与时间的资料放入当前上下文。检索不确定时，允许不召回或向用户确认。删除和更正要能传到索引及缓存。

写入侧优先保存稳定偏好、已确认事实、关键决策和可检验经历，附来源消息、时间与有效范围。临时猜测不要升级为事实；密码等敏感内容不应默认成为长期记忆。按策略在交互结束或后台提取，避免每句话都多调用一次模型。

本项目：仅恢复当前 Session 的历史与摘要；没有跨会话自动记忆。共享待办是业务数据，通过工具取最新状态。后续实现长期记忆时仍按用户隔离，不能把所有窗口聊天直接拼在一起。

讨论重点：记住答案与记住“答案成立的条件”有什么区别？怎样证明检索收益大于引入旧事实的风险？

参考：[LangChain Memory 概念](https://docs.langchain.com/oss/python/concepts/memory)。

### 2. 经典框架、发展趋势和代表实现

先用信息职责组织设计：短期工作记忆服务当前推理；长期语义记忆保存相对稳定的事实和偏好；情景记忆保存事件与经验；程序性记忆保存规则和操作方法。这些是分析维度，不要求一定各建一个数据库。

完整链路是“提取／写入 → 存储与更新 → 检索 → 重排与验证 → 放入当前上下文 → 反馈与删除”。向量库只是存储／检索的一部分，不能替代冲突处理、权限、时效、来源与评估。

代表路径可以这样比较，不能据此认定市场排名：

| 路径 | 参考实现 | 适合关注的问题 |
| --- | --- | --- |
| 线程状态和命名空间长期存储 | LangGraph／LangChain 文档 | 当前执行状态与跨线程知识的边界 |
| 由 Agent 管理的持久状态与记忆 | Letta | 工作上下文与外部记忆的交换、管理策略 |
| 独立记忆层 | Mem0 | 从应用分离提取、更新和检索能力 |

从这些实现可以归纳的工程方向是：记忆从“无限追加历史”走向选择性写入、可更新事实、可追溯召回和权限隔离。是否有效仍要用特定任务集评估，不能靠厂商宣传或记忆条数判断。优先测召回正确率、错误事实率、旧记忆干扰、延迟和删除有效性。

本项目：优先把短期 Session 管理做正确；后续再独立接入长期记忆，不为笔试引入完整记忆服务。

参考：[LangChain Memory](https://docs.langchain.com/oss/python/concepts/memory)、[Letta 源码](https://github.com/letta-ai/letta)、[Mem0 源码](https://github.com/mem0ai/mem0)。

## 模块三：Task

### 1. 长程任务忘记目标的解决方案及取舍

将目标和执行状态从模型临时上下文中移出：持久化用户目标、完成标准、约束、计划、已完成步骤证据、当前步骤和阻塞原因。在阶段边界重新读取，并让工具结果更新可检验的进度。计划可以修改，但修改理由和用户约束要保留。

| 手段 | 收益 | 代价与风险 |
| --- | --- | --- |
| 当前目标＋短检查清单 | 成本低，减少跑偏 | 容易把打勾当完成，必须绑定结果证据 |
| 持久化任务状态与检查点 | 中断可恢复，便于审计 | 恢复不能重复写入，需要幂等和状态核对 |
| 分阶段执行与重新规划 | 缩小单次上下文，适应变化 | 规划有额外成本，交接可能丢失限制 |
| 阶段性验证／反馈 | 发现错误和虚假完成 | 测试本身也可能不完整，需要明确边界 |

完成判断应同时看：目标对应的产物是否存在、必要动作是否成功、有无未处理失败、验收是否通过。模型返回最终文本只代表一次循环结束，不证明业务任务已成功；预算用完更不等于完成。

本项目：有调用／工具／时间预算、历史证据、Trace 和停止恢复记录；用户 todo 是共享业务待办，不充当内部任务管理器。首版重启只恢复历史，不自动续跑；完整长期任务状态是扩展项。

参考：[Anthropic Long-running Harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。

### 2. 每天 9 点总结昨天聊天，如何设计？

这是持久化调度，不是让模型在进程里睡到早上。保存用户时区、9 点规则、启用状态、数据范围、输出位置及授权。按用户本地日期确定“昨天”，不能简单减去 24 小时；时区切换和夏令时要有明确规则。

调度器产生唯一任务键 `user_id + local_date + job_type`，持久队列领取后执行。读取昨天有权访问的聊天，按 Session 分组、按完整交互分批汇总，再汇总成“完成、问题、决策、后续行动”；保留来源与日期。没有聊天时按用户设置静默或输出明确的空结果。

以唯一键、租约、完成状态和幂等结果保存处理重试；补跑是否允许、最多补几天、失败后如何通知，都需要产品规则。先保存结果再通知，通知独立去重，避免“生成成功但发消息失败”触发重新总结。邮件或其他外部发送需有明确授权。

本项目：未实现调度和通知。可以复用 Context 的分批输入能力与工具服务，但不能用当前内存 Session 队列直接冒充可靠调度器。

讨论重点：服务器 9 点离线，11 点恢复要不要补跑？如果用户修改／删除昨天聊天，已生成复盘是否重算？这属于明确的业务选择。

## 模块四：Tool / Session Runtime

### 1. 异步工具的执行和完成通知

先澄清：Python 的 `async def` 只是实现方式；产品意义上的异步工具是可在当前模型轮次之外继续运行、稍后交付结果的任务。短 HTTP 请求可 await；长渲染或批处理更适合提交后返回 job ID。

扩展设计：工具提交返回 `job_id/status`，后台 Worker 用持久队列执行；存储 owner、session、run、输入摘要、幂等键、期限、进度和结果引用。完成事件先持久化，再投递给 Session 的串行事件入口。只有状态从运行转为终态时发一次逻辑完成通知；传输可以重发，消费必须去重。

用户可继续交互，Runtime 把完成结果作为结构化资料供下一次模型调用使用，或以明确通知展示。不能把另一个任务结果随意塞成当前 assistant 调用的 tool 消息；协议需要配对，跨轮完成可以使用专用事件资料或查询 job 工具。取消需区分请求取消、已停止、外部效果已发生和无法确定。

本项目：模型同批独立只读工具可以并发，但仍等待整批完成后继续推理；没有后台 job。可以复用执行记录／事务／SSE，但需新增持久任务表和完成事件。

讨论重点：什么情况下通知用户就够了，什么情况下必须唤醒 Agent 才能完成后续动作？

### 2. Busy 时新消息和异步完成事件同时到达

核心约束是每个 Session 只有一个推进执行状态的入口。事件带类型、顺序号、归属和去重键，状态变化按确定顺序处理；UI 和后台 Worker 不直接改模型历史。

本项目策略：普通消息排队；引导绑定当前 Run，整批工具完成后、下一次模型调用前注入；最终回答阶段收到引导也会继续。停止取消当前 Run 并保留证据，再执行下一条。断线取消该客户端队列；不同 Session 可并行，共享待办用事务与版本控制。

未来加入异步完成：先存结果，进入事件队列。在当前不可打断的提交点之后消费；根据原任务状态决定交给下一次调用、生成独立通知，还是只保留历史。已取消任务的外部完成不能复活原 Run，已完成任务也不应悄悄重新执行。

竞争测试应覆盖最后一个 token 与引导并发、取消与写入提交并发、重复完成事件、旧 Run 的晚到结果，以及两个窗口改同一个待办。锁保护状态判断和提交，长模型请求不应一直占用全局控制锁。

讨论重点：为什么一个全局 `busy` 布尔值不足以支持多用户多窗口？状态归属必须至少细化到 Session／Run／客户端。

## 模块五：Agent Runtime 架构对比

### 1. Claude Code 与 GLM／豆包兼容 Function Calling 的工具方式

先分三个层次：模型 API 协议、Agent Runtime、终端／网页展示。Claude Code 是产品和 Runtime，GLM／豆包是模型服务类别；直接拿界面显示和接口 JSON 比较会混淆层次。这里以 Anthropic 官方工具协议和 GLM 官方兼容接口为可核验依据，不声称已逆向验证 Claude Code 私有实现或所有豆包端点。

Anthropic 官方协议使用类型化内容块，模型返回 `tool_use`，客户端执行后通过带关联 ID 的 `tool_result` 返回。OpenAI-compatible 常见方式是 assistant 的 `tool_calls`，函数参数是 JSON 字符串，结果以 `role=tool` 和 `tool_call_id` 返回。两者都可以结构化调用工具，不能概括成“Claude 纯文本，国内才是函数调用”。

| 维度 | 内容块协议 | 兼容 Function Calling |
| --- | --- | --- |
| 结构 | 同条消息组合不同类型块 | 消息字段承载调用，结果用 tool 角色 |
| 参数处理 | 按块解析类型和输入 | 增量拼接参数字符串，结束后 JSON 校验 |
| 工程取舍 | 多类型内容表达自然，但适配器需理解块语义 | 接口生态统一，但兼容程度和扩展字段需逐家验证 |

工具执行、权限确认、超时、并发、输出截断和 UI 展示属于 Runtime 的工作，不能仅由协议外形推出。供应商也可能提供服务端工具，这与本地执行函数又是另一条边界。

本项目选择兼容协议减少首版接入成本，适配器统一成 `ModelReply(text, calls, finish_reason, usage)`。参数片段拼接完整且 finish 标记有效后才校验执行；页面显示工具卡片，工具结果仍按 API 协议回传。没有获取或展示模型隐藏思维链，只展示公开输出、调用与执行证据。

参考：[Anthropic Tool Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)、[GLM Function Calling](https://docs.bigmodel.cn/cn/guide/capabilities/function-calling)、[OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)。

### 2. OpenHands 状态机的优缺点，以及可替代设计

先固定所看的版本：本次读取 OpenHands 软件 Agent SDK 的 `conversation/state.py`；在线 main 会变化，不能把观察扩展到全部历史版本。源码中的执行状态包括 IDLE、RUNNING、PAUSED、WAITING_FOR_CONFIRMATION、FINISHED、ERROR、STUCK、DELETING，并结合事件日志和状态视图；不是只有一个枚举。

优点是生命周期明确，暂停／确认／错误可独立表达，UI、控制逻辑和恢复有共同语义，事件历史可辅助审计。复杂度来自多个维度：执行阶段、用户授权、后台任务、连接状态和恢复状态若硬合成一个枚举，会造成组合膨胀；若多个地方自行转移，会难以解释并发边界。这里是需要审查的设计风险，不是断言该仓库已经存在所有这些问题。

一种更便于推演的方案：保留少量生命周期状态，把连接、确认、任务与执行步骤拆成独立记录；所有外部输入成为有序事件，通过明确 reducer／转移函数得到新状态和待执行动作。副作用执行结果再作为事件返回；持久化序号、幂等键和状态版本，能重建视图并阻止旧结果覆盖新状态。

这种方案也有代价：事件版本迁移、重放兼容、投递与副作用幂等更复杂。它不是天然更优雅的必选项，小项目用单 Session 串行入口、少量状态和清晰取消语义通常更容易验证。

本项目：Run 使用 queued/running/completed/cancelled/failed/limited/interrupted，Session 串行 lane 和控制锁负责边界，SQLite 保存消息与事件。尚未实现完整事件溯源，进程内队列也不支持多实例；若扩展再迁移为持久事件队列和原子领取，不直接增加全局锁。

参考：[OpenHands SDK 概览](https://docs.openhands.dev/sdk/arch/overview)、[本次查阅状态源码](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/state.py)。
