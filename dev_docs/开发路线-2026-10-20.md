## 1. 项目目标与交付范围

从零实现一个最小可用 Agent，能够接入真实 LLM，由模型自主决定直接回答或调用工具，并支持独立会话、持续追问、上下文压缩、执行记录和异常处理。

核心 Agent Runtime 自行实现，不使用 LangGraph、LangChain、OpenHands 或其他 Agent 框架完成主流程。可以参考其设计和源码，使用 FastAPI、Pydantic、OpenAI SDK 等基础库。

本次交付分为两部分：

1. 可运行项目：后端、前端、测试、README、AI Prompt 和问题解决记录。
2. 架构题研讨材料：十道题全部梳理；最终由毛毛选择每个模块理解最深入的一题提交，共五题。

### 1.1 首版明确包含

- 纯文本输入和真实 LLM 调用。
- 原生 Function Calling、自写执行循环和工具注册机制。
- `calculator`、模拟 `search`、`todo` 三个工具。
- 演示用户 A／B，以及同用户多窗口、不同 Session 同时对话。
- 普通消息排队、当前任务引导、停止、断线取消及历史恢复。
- SQLite 持久化、共享待办面板、全局模型与运行设置。
- 基础 Context 压缩、执行预算、自动重试、Trace 和针对性测试。

### 1.2 后续扩展

- Jev 决策层，首先验证其相对于统一 Agent 的实际收益。
- 图片等多模态输入；确实需要多模态前置决策时，再考虑 Decisions API。
- 真实搜索、跨会话自动记忆、长期任务恢复、定时任务和多实例运行。

首版不实现意图分类和 `chat / agent` 双路径，所有消息统一进入 Agent。用户待办也不等于 Agent 内部的执行计划。

## 3. 自写 Agent Runtime

### 3.1 基本循环

```text
接收请求并进入 Session 队列
          ↓
开始执行，固定模型与设置快照
          ↓
读取会话，组装并检查 Context
          ↓
调用模型，接收并解析输出
          ├─ 普通回答 → 检查待处理引导 → 正常结束或继续调用
          └─ 工具调用 → 校验 → 调度执行 → 保存结果 → 再次调用模型
```

模型负责理解目标、选择工具、生成参数和答案。Runtime 负责输入、协议解析、验证、执行、状态、持久化、预算及退出。

不写死“先搜索、再计算、再写待办”。有结果依赖时，模型必须分步骤调用；同批串行也不会自动把第一个工具的结果填进第二个工具的参数。

### 3.2 输出解析与执行边界

- 分别处理文本、工具调用名称、调用 ID、参数和结束原因。
- 流式参数按调用索引／ID 拼接，完整接收并验证后才允许执行。
- 输出截断或残缺 JSON 不触发工具，不用猜测修补后的参数执行写入。
- 工具结果必须关联原调用 ID，后续模型输入不能遗留无结果的工具调用。
- 只处理供应商实际公开返回的说明；不采集隐藏推理，不以“思考内容”作为操作成功证据。

### 3.3 结束不等于目标完成

| 情况 | 记录 |
| --- | --- |
| 模型正常回答，且没有待执行工具或引导 | 正常结束 |
| 模型要求补充必要信息 | 本轮结束，等待用户新消息 |
| 次数或时长耗尽 | 达到限制，保留进展 |
| 用户手动停止 | 已取消，原因是用户停止 |
| 客户端断线 | 已取消，原因是连接断开 |
| 服务重启 | 已中断，原因是服务重启 |
| 无法恢复的故障 | 执行失败，保留已确认结果 |

计算结果依据工具返回，待办成功依据数据库操作证据。最终回答说“已完成”不能替代证据。预算耗尽后由 Runtime 生成确定性的执行状态说明，不额外调用模型突破硬限制。

## 4. 工具与 Pydantic 契约

### 4.1 注册与验证

每个工具包含名称、描述、Pydantic 参数模型、执行函数及执行模式。

```text
Pydantic 参数定义
   ├─ model_json_schema() → 模型可见的工具 Schema
   ├─ 参数验证           → 校验模型返回的 arguments
   └─ API 请求验证       → 校验前端业务操作
```

禁止未知工具参数，对 ID、版本等关键字段使用严格类型。Pydantic 检查结构、类型和字段约束；工具业务层检查归属、存在性、版本及事务条件。业务写入前必须通过两层验证。

兼容供应商可能支持不同的 Schema 子集，适配层应验证实际兼容性，不把“兼容聊天”当成“所有工具 Schema 都兼容”。

### 4.2 三个工具

| 工具 | 输入与操作 | 输出与错误 |
| --- | --- | --- |
| `calculator` | 数学表达式；括号、小数、正负号、加减乘除、取余 | 结果；非法语法、除零或超出受限范围时返回明确错误 |
| `search` | 查询词、结果数量 | 固定资料的匹配结果、标题、摘要、稳定来源标识和 Mock 标记；无匹配返回空 |
| `todo` | `add / list / update / complete / delete` | 待办数据、ID、版本或结构化错误 |

- 计算器采用受限语法解析，限制表达式长度和计算规模，不执行任意代码。
- 模拟搜索使用可重复的样例资料；不把查询词包装成搜索结果，不伪装成真实联网检索。
- 待办字段包括 ID、用户归属、标题、备注、待办／已完成状态、版本、创建与更新时间，删除为逻辑删除。
- 修改、完成、删除需要明确 ID 和读取时的版本；冲突后重新查询，不静默覆盖。
- 工具由后端注入用户与 Session，模型不能指定其他用户。
- 同一次操作通过执行标识去重；模型以新 ID 发起的操作不简单按相同文本去重。

### 4.3 并行调度

参考 Pi 的工具执行声明：

| 工具 | 声明 |
| --- | --- |
| `calculator`、`search` | 可并行 |
| `todo`，包括查询 | 串行 |
| 未知或未声明工具 | 串行 |

- 同批均明确可并行时，默认最多并行 4 个。
- 同批包含串行工具时，整批按模型返回顺序执行。
- 运行事件可按实际完成顺序展示，交回模型时按原调用顺序整理。
- 批次预算检查与预留必须协调完成，避免并发绕过调用上限。
- 剩余预算不足以执行整批时，不开始部分调用，记录未执行原因。
- 首版不实现自动业务依赖推断或通用 DAG 调度。

## 5. 用户、Session、队列与停止

### 5.1 数据隔离与多窗口

| 数据 | 作用域 |
| --- | --- |
| 模型连接、摘要模型、运行与压缩设置 | 全局共用 |
| 待办 | 用户级共享 |
| 聊天、摘要、执行状态、消息队列 | Session 级隔离 |
| 事件连接、提交归属 | 客户端／窗口级区分 |

预置演示用户 A／B，仅用于演示身份切换，不宣称提供真实身份认证。

同用户可以打开多个窗口，选择不同 Session，同时执行不同对话。各窗口当前会话独立保存；停止或断线一个窗口，不误停另一个窗口的任务。两个窗口选择相同 Session 时，查看同一历史，普通消息进入同一个执行队列。

跨 Session 待办冲突依靠数据库版本检查解决，不能仅依靠单 Session 串行。

### 5.2 发送与引导

- 普通发送默认排队，一个 Session 同时只有一个 Agent 执行。
- 引导属于当前任务，按接收顺序保存，在下一次模型调用前加入。
- 当前模型请求和工具不会因为引导自动取消。
- 整批工具结果补齐后再加入引导，不破坏调用／结果配对。
- 在最终回答期间收到引导，当前调用结束后继续处理，仍归属当前任务。
- 引导展示“等待生效／已加入上下文”；加入不等于已满足。
- 引导使用用户补充消息身份，不提升为系统指令，也不重置预算。
- 接收引导与结束任务必须协调，避免已接收引导被静默遗漏。

### 5.3 手动停止

1. 前端立即停止展示当前任务后续输出，后端设置取消信号。
2. 尝试取消在途模型、摘要或工具执行，不再启动剩余工具。
3. 已收到模型文字保留，并记录“已被用户手动停止”。
4. 工具取消原因和已确认的业务结果分别保存；成功提交的待办不自动回滚。
5. 未执行的有效工具调用补取消结果；残缺参数仅保留诊断记录，不进入可执行上下文。
6. 当前任务完成清理后，自动执行下一条仍有效的排队消息。

本地停止接收不能保证远端服务立即停止计算。SQLite 写入进入提交阶段时，要核实结果；不能一边尚未确认写入，一边在相同 Session 启动下一任务。

### 5.4 断线与服务重启

- 页面内切换会话保持连接，不算断线。
- 后端检测到页面关闭、刷新或网络断线时，取消该客户端当前任务，并一并取消其尚未执行队列。
- 断线原因使用“连接断开”，与“用户手动停止”分开。
- 迟到输出不能追加到已停止的回答，也不能污染下一任务。
- 重连恢复历史和最终状态，不自动重跑中断任务或已取消队列。
- 后端重启后，保留历史、摘要、待办和设置，标记遗留执行中断、队列取消，不自动恢复执行协程。
- 失败或停止后，通过新消息继续；新任务使用新预算并读取已有证据，不整轮重放。

## 6. 模型设置、预算与重试

### 6.1 全局模型设置页

通过连接名称、`base_url`、API Key 和模型名配置 OpenAI-compatible 服务，调用统一由后端发起。连接列表不可用时仍允许手动输入模型名。

保存或修改模型连接时自动发起短请求测试，并尝试读取对应模型的 Context 容量。模型容量按连接与模型分别保存，切换模型重新检测。

- 能读取容量：使用读取值，并展示来源。
- 不能读取容量：默认 256K，即 262,144 tokens，并标记“默认值”。
- 不假设标准 `/models` 接口一定提供容量，不把任意同名字段的字符长度当作 Token 容量。
- 连接测试与 Function Calling 全能力验收分开；一次聊天成功不等于所有能力通过。
- API Key 只在后端保存；接口回读只返回掩码，日志与 Trace 不保存密钥。
- 摘要默认复用对话模型，可以另选连接及模型；独立摘要模型也要检测容量。

### 6.2 已确认的运行默认值

| 项目 | 默认值 |
| --- | ---: |
| 单次任务模型调用上限，包含摘要与重试 | 20 次 |
| 单次任务工具调用上限 | 40 次 |
| 单次任务总时长 | 300 秒 |
| 单次模型请求超时 | 60 秒 |
| 单次工具超时 | 10 秒 |
| 模型自动重试 | 3 次，首次加重试最多 4 次尝试 |
| 重试等待 | 每次 30 秒 |
| 工具并行上限 | 4 |

全部设置全局共用并允许调整；任务开始时固定配置，修改只影响后续开始的任务。排队时间不计入执行时长，执行中的重试等待计入总时长。单次超时不能超过剩余总时长。

只对可恢复的模型网络／限流／上游故障应用自动重试。SDK 隐式重试关闭，由 Runtime 统一记录和计数。供应商明确要求更长等待时遵循该要求；剩余预算不足则停止，不保证重试满三次。

认证错误、非法请求、Context 超限、已流式输出部分回答和不确定的工具写入，不直接套用临时故障重试。

## 7. Context 管理

### 7.1 输入组成

```text
系统指令与工具定义
        +
会话摘要：目标、约束、事实、操作证据、未完成事项
        +
近期完整交互
        +
当前请求、已加入引导、最新必要工具调用及结果
```

聊天记忆仅在当前 Session 内恢复，不自动读取其他 Session 的聊天。待办按用户共享，通过工具按需读取最新状态。摘要中的待办状态只表示当时发生过什么，不能替代当前数据库状态。

### 7.2 容量与压缩

```text
可用输入空间 = 当前 Context 容量 − 输出预留 − Token 估算余量
```

- 不再设置固定 16,000 tokens 输入上限，按检测容量或默认 256K 计算。
- 每次模型调用前检查输入；达到可用空间的 80% 时触发压缩，目标为约 50%。
- 保护用户当前请求、已生效引导、目标和约束、未完成事项及最新必要工具交互。
- 较早对话以及当前任务中已完成的较早步骤可以进入摘要。
- 按完整交互与 Token 预算选边界，不机械固定“最近四轮”，不拆散工具调用／结果。
- 50% 是目标；不能为了凑目标删除必要要求。压缩后仍不满足容量时明确停止。
- 完整历史和完整工具结果继续存储；只对模型输入做摘要或有标记的结果长度限制。

优先使用匹配分词器；无法匹配时保守估算并标注。包含工具 Schema 和消息结构开销，保留余量，并记录实际用量与估算差异。

### 7.3 摘要生成和覆盖范围

- 默认复用对话模型，可独立配置；摘要调用不提供业务工具。
- 以旧摘要加上这次移出的历史增量生成新摘要。
- 分批大小由摘要模型自身容量决定，不能默认它能容纳主模型的输入。
- 只推进实际成功处理的历史范围；不能裁掉大部分摘要输入，却把整段历史标为已覆盖。
- 摘要保留来源标识、待办 ID、版本、取消与失败状态，不把计划写成已成功执行。
- 覆盖范围与版本由程序维护；新摘要生成成功后再替换旧摘要。
- 摘要失败但原上下文仍能容纳时，可以继续使用原上下文；已经超限则保留数据并停止本轮。
- 用户停止摘要时，取消调用并记录手动停止，不替换旧摘要、不推进覆盖范围。

### 7.4 仍需通过真实模型验证的初始参数

以下来自讨论中的初始建议，不代表已验证的最优数值；设置页允许调整：

| 参数 | 初始建议 |
| --- | ---: |
| 单次最大输出 | 2,000 tokens，须符合所选模型限制 |
| 摘要输出上限 | 1,000 tokens，须测试关键约束保留效果 |
| Token 估算余量 | 实施时明确计算方法并记录，不能声称通用估算精确 |

输入、输出及余量必须共同满足模型限制；容量回退值也不代表供应商保证接受该容量。

## 8. 前端、接口与观测

### 8.1 页面

- 左侧：演示用户切换、会话列表。
- 中间：消息、工具卡片、执行与排队状态、输入框、发送／引导／停止。
- 右侧可收起：当前用户共享待办，支持手动操作，与 Agent 共用业务服务。
- Trace 抽屉：模型／工具调用、参数和结果、耗时、重试、摘要、引导及停止。
- 全局设置：模型连接、摘要模型、预算与重试、Context 策略。
- Context 状态：估算使用量／容量、容量来源、压缩状态、可展开摘要与压缩前后用量。

常规进度保持简洁，详细证据集中在 Trace；不新增一套重复的诊断入口。

### 8.2 接口职责

| 接口组 | 能力 |
| --- | --- |
| 用户／Session | 演示用户列表、创建和查询会话、读取历史 |
| 执行控制 | 提交消息、提交引导、取消指定任务 |
| 事件订阅 | 按客户端订阅执行与待办变更事件 |
| 待办 | 查询、新增、修改、完成、逻辑删除 |
| 全局设置 | 管理连接、自动测试和容量读取、默认模型、运行策略 |

提交消息立即返回任务 ID 和队列状态，客户端请求 ID 用于防重复入队。停止请求指定任务 ID，不使用容易发生竞争的“停止当前任务”隐式指代。

事件至少包含事件 ID、Session ID、任务 ID、类型、时间与数据；工具事件包含调用 ID。客户端归属用于隔离断线取消范围，不替代业务用户归属检查。

### 8.3 持久数据

保存演示用户、Session、消息、任务及输入队列、引导、工具调用及结果、操作去重记录、摘要与覆盖范围、待办、全局设置和执行事件。进程内协程、锁与连接不作为可直接恢复的数据库对象。

## 9. 验证方案

### 9.1 离线验证

使用可控模型响应、故障和时钟，不把离线结果当成真实供应商验证。

| 类别 | 关键场景 |
| --- | --- |
| 参数与工具 | Schema 一致、非法参数、除零、空搜索、归属、版本冲突、写入去重 |
| 模型解析 | 文本与工具区分、流式参数拼接、多调用、截断、残缺 JSON、调用结果配对 |
| 调度与预算 | 并行上限、todo 整批串行、整批预算预留、模型／工具／时长限制 |
| 重试 | 三次重试、30 秒间隔、预算耗尽、非重试错误、部分输出后失败 |
| Session | 同会话排队、跨会话并行、跨用户隔离、同用户待办共享 |
| 引导与停止 | 运行中与末尾引导、停止、断线取消全部归属队列、迟到事件、结束竞争 |
| Context | 容量读取／回退、80% 触发、完整交互边界、分批摘要、覆盖范围、失败和取消 |
| 恢复 | 重启保留数据，遗留任务中断，不自动重放 |

测试替换实际等待时钟；用小容量配置重复触发 Context 压缩，不依赖长时间等待或海量输入。

### 9.2 真实模型与页面验收

1. 普通聊天直接回答，工具由模型自主选择。
2. 搜索、计算、待办组合任务及后续修改。
3. 纯聊天追问、工具结果追问、摘要后的续聊。
4. 同用户两个窗口、不同 Session 同时执行。
5. 停止或断线其中一个窗口，不影响另一个窗口。
6. 待办面板和 Agent 操作一致，跨窗口冲突可解释。
7. 模型、工具、重试等待和摘要期间停止，历史正确。
8. 真实模型的流式工具调用与 Context 行为。
9. 后端测试、前端类型检查和构建。

验证记录区分“通过、失败、未执行”，附模型、连接类型、配置快照及失败样例。启动服务或调用真实模型必须在相应阶段获得明确授权；本次文档生成不包含这些操作。
